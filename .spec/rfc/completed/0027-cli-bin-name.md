# RFC 0027: CLI Bin Name

**Status:** Implemented

## Summary

Rename the published executable from `opencode-plugins` to `plugins`, so the command a user gets matches the name the CLI already prints in its own usage screen.

## Problem

The package declares one bin, `opencode-plugins`, while every user-facing string in the CLI — the usage screen, the log frame header, the banner — says `plugins`. The two disagree, so a user who reads the help screen and types `plugins add` gets "command not found".

The name is also a leftover. At the first commit this project was OpenCode-only: the usage screen read `opencode-plugins add`, the header read `opencode-plugins`, and clones cached to `~/.cache/opencode-plugins`. The project was later generalised to eight targets and the output was renamed to `plugins`, but the bin name was not.

The name is additionally misleading now. OpenCode is a real product by Anomaly and is itself one of this CLI's eight install targets. Naming the executable `opencode-plugins` implies a tie to that product that does not exist, and invites confusion with Anomaly's own tooling.

## Goals

Make the installed command name and the name the CLI displays the same word, and stop implying a product relationship that does not exist.

## Non-goals

Renaming the npm package, which stays `@borg0ai/plugins`. Changing any other user-facing wording, since the usage screen and header already say `plugins` and become correct rather than needing edits. Changing what the CLI does.

## Design

`apps/cli/package.json` declares its single bin as `plugins` instead of `opencode-plugins`. That is the whole functional change. Because the usage screen, the `header(...)` label, and the banner already read `plugins`, they require no edit and simply become truthful.

The generated-file banner in `lib/opencode.ts` reads "Generated by opencode-plugins for ...". It is a comment inside a file the CLI writes into a user's OpenCode config, so it is updated to the same word to keep the provenance line consistent with the tool that wrote it.

`plugins` is a short global name and could collide with another package installed in the same project. That is accepted: the package is already scoped, and `npx @borg0ai/plugins` remains the unambiguous invocation regardless of the bin name.

## Acceptance

Installing the package produces a `plugins` command, and no `opencode-plugins` command. Running `plugins --help` displays usage lines that the same binary can execute, so no line in the usage screen names a command that does not exist. The generated OpenCode adapter's provenance comment names the current tool. `npx @borg0ai/plugins` continues to resolve the package, since the bin name does not affect npx resolution.
